# «Прокорми монстра»: архитектура и структура данных

Документ для промежуточной сдачи (п. 7.1.4 ТЗ). Состояние на 24.09.2026. Коммит `ce6db61` плюс незакоммиченные правки.

## 1. Что это за приложение

Игра о финансовой грамотности для детей 7–11 лет. Ребёнок заводит 3D-монстрика. Каждые три игровых дня он получает бюджет и делит его на обязательные расходы, «веселье» и копилку. Деньги он тратит в магазинах, в экономических эпизодах и дополнительных заданиях. Каждые три дня игра сравнивает план с фактом. Решения ребёнка меняют характеристики монстрика: здоровье, настроение, развитие, сытость, чистоту.

**Текущая платформа — веб-приложение.** Это статическая сборка Vite + Three.js в вертикальной оболочке 9:16. Оно работает в браузере телефона и компьютера и не делает ни одного сетевого запроса во время игры. Чтобы получить Android-APK, эту же сборку упакуем в WebView-контейнер (Capacitor). Платформа при этом не меняется, подробности в разделе 7.

## 2. Технологический стек

| Слой | Технология | Зачем |
|---|---|---|
| Интерфейс | HTML + CSS, ванильный JavaScript (ES-модули) | Экраны, карточки, туториалы, ментор |
| 3D | Three.js 0.170, модели GLB (анимации Mixamo) | Монстрик, комната, парк, магазин, мини-игры |
| Сборка | Vite 6.4 | Бандл, хеширование ассетов, встраивание контента в JS |
| Хранение прогресса | `localStorage` браузера / WebView | Журнал событий профиля |
| Контент | `monster_data_mart_rows.json` (419 строк, 37 типов объектов) | Реплики, туториалы, эпизоды, товары, цели, триггеры |
| Авторинг контента (только для разработчиков) | Таблица Supabase `monster_data_mart` + `scripts/data-mart.js` | Редактирование контента в таблице и выгрузка в JSON |
| Упаковка под Android (план) | Capacitor, Android SDK, minSdk 26 (Android 8.0) | Подписанный релизный APK |

Сервера нет. Supabase в игре не участвует. Таблица нужна только для правки контента: командой `npm run data:pull` она выгружается в JSON, и этот JSON попадает в сборку. Ключ Supabase нужен только скриптам разработчика и в сборку не попадает.

**Принципы разделения:**

- **Контент отделён от кода.** Тексты реплик, шаги туториалов, товары, цены, цели, эпизоды и триггеры лежат в `monster_data_mart_rows.json`. Код ищет строки по `object_type`, `trigger` и `title`. Озвучка лежит в `public/audio/<папка>` и тоже привязана к строке контента (поля `audio`, `audio_folder`).
- **Правила экономики написаны чистыми функциями** без DOM и 3D. Пример: `letterOfCreditVerdict`, `loanVerdict`, `routeVerdict`, `budgetReview`, `budgetDiscrepancies`, `ownershipCost`. На них будут писаться автотесты (план — в таблице требований).
- **Состояние целиком выводится из журнала** (event sourcing). Отдельного «сохранённого состояния» нет, поэтому после перезапуска прогресс восстанавливается однозначно.
- **Слабое место (честно):** `main.js` занимает около 16 тыс. строк и смешивает сценарии экранов разных эпизодов. До финала разнесём его по модулям `screens/*.js`, по одному на экран или эпизод. Логику при этом не меняем.

## 4. Функциональная архитектура: игровой цикл

```
Первый запуск → заставка и знакомство с игрой → редактор монстрика (цвет, уши, рога) → имя
   → инструктаж по уходу → бюджет 1 (городская дотация 100 🪙):
        обязательные | веселье | копилка  →  карман = обязательные + веселье, копилка = копилка
   → Комната (главный экран). Каждый игровой день:
        кормление (корм из магазина) · чистка (раз в 3 дня) · экономический эпизод дня
        · дополнительные задания 📋 · сообщения 💬 · перекладывание копилка ↔ карман
        → выполнено условие конца дня → кнопка «Следующий день»
   → каждые 3 дня: экран «План и факт» → разбор ментора → новый бюджет (от папы)
   → дни 1–9: сюжетные эпизоды; с дня 10 — финальная часть:
        дни идут автоматически с остановками на решения, покупка целей из копилки
   → победа (все цели куплены или накоплено 1500 🪙)
```

**Игровой период** — это период одного бюджета, **3 игровых дня**. Дни к реальному времени не привязаны: день сменяется, когда игрок выполнил условие дня (триггер из контента) и нажал кнопку.

| День | Эпизод / задание | Финансовая тема |
|---|---|---|
| 1 | Первый бюджет | Планирование: обязательное / желаемое / накопления |
| 1 | Магазин продуктов (выбор корма) | Покупки: сравнение по составу и цене за 100 г |
| 2 | «Прогулка в парке» + цель «Праздник огней» | Покупки: мгновенное удовольствие против пользы; постановка цели |
| 3 | «Магазин техники» + цель «Игровая приставка» | Покупки: цена владения против цены на ценнике; взять из копилки |
| 3 | «План и факт» + второй бюджет | Планирование: сравнение плана с фактом, неделимость упаковки |
| 4 | «Смета на теннис» | Планирование: смета, доля участия |
| 5 | «Аккредитивы» · доп. задание «Валютное мемо» | Платежи: условия оплаты сделки; валюты |
| 6 | «Поездка на тренировку» (планировщик маршрута) | Платежи и планирование: оптимальный маршрут по цене и времени |
| 7 | «Кредиты для бизнеса» · доп. задание «Активы и пассивы» | Кредит и ставка; активы и пассивы |
| 8 | Магазин игрушек + цель «Телескоп» | Покупки: польза игрушки, спонтанные траты |
| 9 | «Поломка удалителя козявок» | Сбережения: прогноз срока накопления, запасной вариант |
| 10+ | Финальная часть | Накопление и покупка целей |

На каждом решении работает **ментор**. Он объясняет, почему решение верное или ошибочное, а ошибочную покупку отменяет до того, как спишутся деньги. **Туториал** показывается при первом входе в каждый новый экран. Реплики ментора и туториалы озвучены.

## 5. Хранение данных

### 5.1. Ключи localStorage

| Ключ | Содержимое |
|---|---|
| `prokormi-monstra:user-profile-id:v1` | id активного профиля (UUID) |
| `prokormi-monstra:progress:v1:<id профиля>` | JSON-массив записей журнала этого профиля |
| sessionStorage `prokormi-monstra:launch:v1` | Метка перезапуска при смене профиля (resume / new) |
| sessionStorage `prokormi-monstra:jury-launch:v1` | id эпизода, который запускается в песочнице жюри |

Персональных данных нет. Профиль — это случайный UUID и имя монстрика (до 12 символов). Имя ребёнка, телефон и e-mail игра не спрашивает.

### 5.2. Запись журнала

Каждое действие дописывается в конец журнала. Старые записи не меняются. У всех записей есть `Тип события` и `Профиль пользователя`, у большинства ещё `Игровой день`:

```json
{
  "Тип события": "Сохранение планового бюджета",
  "Профиль пользователя": "3f0c…",
  "Игровой день": 4,
  "Значение": { … }
}
```

Остальные поля зависят от типа события. Основные типы (константы в `room-state.js`):

| Группа | Типы событий | Ключевые поля |
|---|---|---|
| Профиль и питомец | `Создание монстра` | `Имя монстра`, `Характеристики 3D модели монстра` (мех, уши, рога) |
| Дни | `Начало нового дня` | `Порядковый номер дня` |
| Деньги | `Пополнение карманных денег`, `Списание карманных денег`, `Пополнение копилки`, `Списание из копилки` | `Значение` (знак задаёт направление), `Источник средств` |
| Бюджет | `Сохранение планового бюджета`, `Учет фактического бюджета` | `Статьи бюджета` {Обязательные расходы, Веселье, Накопления на большую покупку}, `Фонд к распределению`, `Номер бюджета`, `Цели накоплений` |
| Покупки и инвентарь | `Покупка еды`, `Покупка техники`, `Покупка игрушек`, `Изменение инвентаря пользователя` | `Тип инвентаря` (id строки контента), `Количество`, `Единица измерения` (г / шт) |
| Питомец | `Изменение характеристики монстра`, `Изменение состояния монстра`, `Кормление`, `Чистка козявок` | `Характеристика`, `Изменение`, `Было`, `Стало`, `Причина` |
| Цели | `Появление крупной финансовой цели`, `Решение по крупной финансовой цели`, `Покупка крупной финансовой цели` | `Идентификатор цели`, `Цель принята` |
| Эпизоды и задания | `Экономический эпизод`, `Правильное / Ошибочное решение финансового эпизода`, `Завершение экономического эпизода`, `Выполнение дополнительного задания` | `Идентификатор эпизода/задания`, `Пояснение`, `Решение отменено ментором`, `Ходов`, `Ошибочных ходов` |
| Обучение | `Просмотр туториала …` | `Пропущен` |

### 5.3. Производное состояние

`deriveRoomState(records)` проходит журнал один раз и возвращает:

```
{ day, pocket, savings,                 // день, карман, копилка
  stats: { health, mood, development }, // −3…+3 (настроение до +10)
  hungry, dirty,                        // сытость = кормили в текущий день; грязь до чистки
  inventory: Map<id товара, количество>, foodGrams, suitableFoodGrams,
  decidedSavingsGoals, completedEconomicEpisodes, completedAdditionalTasks,
  devicesInRepair, name, appearance }
```

Отдельные модули добавляют свои производные данные: `budgetReview(records, n)` — план и факт бюджета n, `acceptedSavingsGoals` — принятые цели, `profilesFromLogs` — список профилей.

## 6. Структура контента (data mart)

Одна таблица, одна строка — один объект контента. Тип задаёт `object_type`, русское название типа — `object_type_ru`. Основные колонки:

| Колонка | Назначение |
|---|---|
| `id`, `object_type`, `title`, `text` | Идентификатор, тип, название, текст для ребёнка |
| `trigger`, `queue`, `game_day`, `day_is_it_available` | Когда показать и в каком порядке |
| `price`, `old_price`, `category`, `weight_in_grams`, `store_id` | Экономика товаров и целей |
| `mood_change`, `development_change`, `dirty_on_play`, `unsuitable_reason` | Влияние покупки на питомца |
| `audio`, `audio_folder`, `image`, `image_folder` | Озвучка и картинки |
| `screen_area` (JSONB) | Параметры конкретного типа: цель подсветки в туториале, этапы кейса аккредитива, точки карты маршрута и т. п. |

Объём контента на 24.09.2026: 128 реплик ментора, 104 шага туториалов (14 видов), 6 экономических эпизодов, 2 дополнительных задания, 3 цели накоплений, 3 магазина, 45 товаров (4 корма, 5 товаров техники, 36 игрушек), 9 триггеров конца дня.

**Как добавить задание.** Если это новая строка для существующей механики (реплика, товар, цель, шаг туториала, кейс аккредитива, заявка на кредит), код не меняется: строка добавляется в таблицу, дальше `data:pull` и сборка. Если это новый тип мини-игры, нужен модуль правил и экран. Условие доступности и туториал при этом берутся из контента. См. вопрос к заказчику № 7.

## 7. Сборка и развёртывание

| Что | Как | Статус |
|---|---|---|
| Веб-сборка | `npm ci && npm run build` → `dist/` | Работает |
| Веб-демо для экспертов | Yandex Object Storage (`npm run deploy:yandex`), открывается из РФ без VPN | Работает |
| Android APK | Capacitor: `dist/` → `android/`, `minSdkVersion 26`, портретная ориентация, без разрешений; подпись релизным ключом вне репозитория | План |
| Репозиторий | github.com/Evsikoff/prokormi | Работает |

**Главный технический риск — размер ассетов.** Каталог `public/` весит около 670 МБ, `dist/` — около 750 МБ: видео, музыка, озвучка WAV, 3D-модели. Для APK план такой: перекодировать видео (H.264, 720p), озвучку перевести в OGG/MP3, текстуры сжать (KTX2/WebP), лишние варианты моделей удалить. Цель — APK до 150 МБ. Параллельно нужно проверить время запуска на устройстве с 3 ГБ ОЗУ.

## 8. Режим проверки (демонстрационный)

Панель жюри: удерживать кнопку 👥 три секунды. Контент в ней сгруппирован по типам. Кнопка ▶ у эпизода или задания перезапускает игру в **песочнице** `jury-sandbox`: это копия монстрика игрока на нужном дне, в кармане и копилке по 100 🪙. Кнопка ▶ у реплики проигрывает её озвучку. Прогресс игрока в песочнице не меняется, после перезагрузки игра возвращается к его профилю. Сквозного прохода пяти периодов подряд пока нет (см. таблицу требований, п. 2.5.13).
